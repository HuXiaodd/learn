1. std::vector —— 高性能转发的首选

底层： 实际上就是一段连续的内存（类似 C 语言的动态数组 malloc 出来的）。
优势： 遍历极快，因为内存连续，对 CPU Cache 非常友好。
代价： 在中间插入/删除元素需要搬移内存（O(n)）。
面试陷阱： reserve() 和 resize() 的区别？
reserve(n) 只分配内存，不创建对象,它只改变 capacity（容量），不改变 size（大小）。
resize(n) 分配内存并调用构造函数创建对象，它既改变 capacity 也改变 size。

2. std::list —— 别被它的 O(1) 插入骗了
底层： 双向链表。

现实： 虽然插入/删除是 O(1)，但因为内存不连续，每次访问都要去找指针（Cache Miss 严重）。在高性能场景（如你的云网关项目 ）中，很少使用。

3. std::unordered_map（hash桶） vs std::map（树） —— 查找的艺术
std::unordered_map（哈希表）： 平均查找 O(1)。
对应你的项目： 你简历中提到的“哈希桶存储流表” ，在 C++ 中对应的就是这个容器。
std::map（红黑树）： 查找 O(log n)。
特点： 元素是有序的。如果需要按顺序遍历键值，选它

std::vector 的几何增长与迭代器失效底层实现： 它是对 malloc/realloc 的高级封装。
在内存中维护三根指针：_Myfirst（首地址）、_Mylast（当前元素末尾）、_Myend（可用内存末尾） 。
增长算法： 当 _Mylast == _Myend 时触发重分配。大多数实现（如 GCC 的 libstdc++）采用 2 倍增长，而 MSVC 采用 1.5 倍。
深度细节： 为什么要 1.5 倍或 2 倍？这是为了在多次分配后，先前释放的内存块有可能被重新利用（2 倍增长在数学上永远无法重用之前的块）。
性能陷阱： * 搬移开销： 触发重分配时，会调用元素的移动构造函数（如果支持）或拷贝构造函数，将旧内存数据“搬家”。
这在 DPDK 这种追求纳秒级响应的场景是致命的。
迭代器失效： 一旦内存重分配，所有指向原内存的指针/迭代器全部变成野指针。
优化： 必须使用 reserve(n) 预留空间，避免中间过程的频繁 realloc 。

2. std::unordered_map 的哈希冲突与 Rehashing你简历中提到的“哈希桶存储流表” ，对应的就是这个容器。
底层结构： 数组 + 单链表（或红黑树，取决于实现）。查找深度： 平均 $O(1)$。但当 Load Factor（装载因子，即 元素数/桶数） 超过阈值（默认 1.0）时，会触发 Rehash。
内存代价： Rehash 会申请一个约两倍大小的新桶数组，并重新计算所有元素的哈希位置。这对实时性要求高的机器人控制逻辑来说，会产生明显的延迟抖动。
Cache 友好度： 极差。因为链表节点在内存中是离散分配的，每次通过 next 指针跳转都会大概率触发一次 Cache Miss。

2. WebSocket —— 真正的双全工
痛点： HTTP 只能客户端问、服务器答。但在机器人场景中，服务器需要主动推指令给机器人。
原理： 先通过 HTTP 握手，然后“升级”（Upgrade）为 WebSocket 协议。之后，这条 TCP 连接就变成了长连接，双方可以随时发数据。
与 MQTT 的区别：

MQTT 适合低带宽、不可靠网络、一对多（发布/订阅）。
WebSocket 适合 Web 浏览器端与服务器的一对一实时通信。

1. 握手阶段（Upgrade 机制）
WebSocket 并不是直接建立的，它借用了 HTTP 的通道进行“换装”：
客户端发送 HTTP GET： 头部包含 Upgrade: websocket 和 Connection: Upgrade。
密钥挑战： 客户端发一个 Sec-WebSocket-Key（随机 Base64 字符串）。
服务器响应： 状态码 101 Switching Protocols。服务器将 Key 与一个固定的 GUID 拼接，进行 SHA-1 哈希后再转 Base64，回传 Sec-WebSocket-Accept。
目的： 这不是为了加密，而是为了向客户端证明：“我真的理解 WebSocket 协议，不是一个误打误撞的普通网页服务器”。

2. 数据传输阶段（二进制帧）
一旦握手完成，TCP 连接就不再传输 HTTP 报文，而是传输 WebSocket Frame。
帧头结构： 仅有 2 到 14 字节的额外开销（相比 HTTP 数百字节的 Header，极其轻量）。
掩码（Masking）： 客户端发往服务器的数据必须经过随机掩码处理。这是为了防止某些中间代理服务器将 WebSocket 报文误解为 HTTP 缓存。
