虚函数表（Virtual Table）—— 多态的真相
在 C 中，你可能用函数指针数组来实现类似“多态”的功能。C++ 自动帮你做了这件事。

核心逻辑： 每一个拥有虚函数的类，编译器都会为其创建一个虚函数表（vtable），里面存储了函数指针。

内存开销： 类的每个对象实例都会多出一个隐藏指针（vptr），指向这个表。

答复：
你的疑问非常敏锐：如果继承链是 C -> B -> A，用 B 指针指向 C 并删除， A 的析构函数会被调用吗？
结论是：肯定会调用。底层逻辑：虚析构的“传染性”： 只要基类 A 的析构函数被声明为 virtual，其所有派生类（B 和 C）
的析构函数在虚函数表中都会被标记为虚函数，即便你没在 B 或 C 中显式写 virtual 。调用顺序： 析构过程确实像“剥洋葱”。
虚函数表记录的是最顶层子类的析构函数入口。当调用 delete ptr_to_B 时：系统发现 B 的析构是虚的，于是去虚表中找到真正
的实例（C）的析构函数 。执行 C 的析构函数体（释放 C 特有资源）。
关键点： 子类的析构函数执行完毕后，编译器会自动生成的代码去调用其直接基类（B）的析构函数，接着 B 再调用 A。它不是“调用栈”：
 虚函数表只存了一个入口指针。一旦进入这个入口（最子类的析构），后续向基类回溯的调用是由编译器在编译阶段就织入代码中的固定行为
 ，不依赖虚表。

struct B {
    std::weak_ptr<A> a_ptr; // 改为弱引用

************************************************************************
1. 核心架构：发布/订阅（Pub/Sub）
MQTT 不是点对点的（和 HTTP 不同），它通过一个 Broker（代理） 中转。

Topic（主题）： 类似于频道（如 /robot/sensor/lidar）。

Payload（负载）： 实际发送的数据，通常是 JSON 或二进制。

2. 三种服务质量（QoS）—— 面试高频
面试官可能会问：“在网络不稳定的情况下，你怎么保证机器人指令一定到达？”

QoS 0： 最多一次（可能会丢，适用于不重要的传感器数据）。

QoS 1： 至少一次（保证到达，但可能会重复）。

QoS 2： 只有一次（通过四次握手保证不丢不重，代价最高）。

3. 遗嘱消息（Last Will and Testament）
这是机器人最常用的功能：如果机器人意外断网，Broker 会自动向指定频道发一条消息（如“设备离线”），方便后台监控

MQTT 不是请求-响应（Request-Response），而是异步事件流。

连接（Connect）： 客户端（你的机器人）向 Broker 发起连接，携带 ClientID。
订阅（Subscribe）： 客户端告知 Broker：“我对 /cmd/move 这个主题感兴趣。”

### 2. 为什么需要回调（Callback）？
因为它是异步的。在 C 语言开发中，你通常需要设置一个 on_message 函数指针。当 Broker 推送报文过来时，底层库（如 mosquitto 或 paho）会触发这个回调。
你的理解偏差修正： > 并不是“我发信息给他，他回答时附带信息”。那是 HTTP 的逻辑。
在 MQTT 中，如果你发了消息（Publish），你通常不期望对方立刻回。如果你需要对方回，对方必须发布（Publish）到另一个你订阅的主题上。
