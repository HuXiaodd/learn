Q:设计模式
1.策略模式
A:将“怎么做”与“什么时候做”解耦。
在网络开发中，你可能需要支持不同的 Hash 算法或不同的限速策略。
做法：定义一个包含函数指针的结构体。
实际上,策略模式是定义一个函数范式,在主体流程不变的情况下,其他功能可以随意改动实现函数.
面试点：增加新算法时，不需要修改主逻辑代码（符合开闭原则）
new quest:什么是开闭原则?可以解释一下吗？就是新功能尽量使用新代码,而不是修改旧逻辑
a:当需求变化（比如增加一种新的加密算法）时，你应该通过增加新代码来解决，而不是去改动已经测试好的核心逻辑

2.观察者模式的形式
A:事件驱动的形式,着重点在什么时候发生了什么事情,把所有的事务的处理函数注册表列出来,让其他事务的处理函数来注册这个函数。
面试点：模块间解耦。收包模块不需要知道业务模块的存在，只需执行回调。

3.单例模式 (Singleton Pattern)
A:这个模式需要满足的前提是,全局只有一个可用资源,这个模式下无可避免会出现竞争,所以循环也好,队列也好,所有使用者只能拿一个句柄
使用时需要考虑竞争,初始化时,所有线程只能初始化单个唯一句柄。
面试点：双重检查锁定 (Double-Checked Locking) 和线程安全。
new quest:双重检查锁定是什么？其实就是先判空再加锁。
逻辑：
先检查指针是否为空（不加锁），如果已经初始化了，直接返回。
如果为空，才加锁。
关键点：加锁后再次检查指针是否为空。因为在加锁的过程中，可能有其他线程刚刚抢先完成了初始化。

4.抽象工厂 / 接口封装
对于此模式中,其实本质是把所有的操作拉出来形成一个操作集合,在实现中对于不同种类的相同操作,
只需定义不同名的操作集合,并对应整理各个功能的操作到对应集合里,就实现了一组接口对不同事情的操作集合.

5.Reactor 模式 (反应堆模式)
提炼：高性能并发服务器的“指挥官”。
这是高并发 C 开发者的必考题。它不是单一的函数，而是一套流程：
Event Loop：通过 epoll_wait 监听文件描述符。
Demultiplexer：当有事件（读/写）时，将事件分发出去。
Handler：对应的业务处理函数。

6.状态模式
状态机+跳转表的形式,把单事务的不同状态需要执行的函数通过一次循环所有状态并按状态执行跳转函数的
方式实现.

7.迭代器模式
其实这本身就是对不同数据结构增删改查的封装.上层根本无需知道迭代器内部实现.

8.代理模式
其实就相当于一个中间过渡区,在上层需要实现一种功能时,其实使用的是中间过渡区的功能,并不直接调用最底层的功能
面试点：这就是 AOP（面向切面编程）在 C 语言里的体现。利用代理模式实现非侵入式的监控。

9.对象池模式
与其说是一种模式,不如说是一种内存分配方式,使用内存池去单独存储一种结构,并预先分配出来.

*****************************************************************************
经典问题:流表老化

结构设计：采用 Cuckoo Hash 保证 $O(1)$ 查找。使用 __attribute__((packed)) 和缓存行对齐优化结构体。
老化逻辑（你的核心改进）：摒弃 $O(n)$ 线性遍历，采用 分级时间轮。引入 “单次限额处理”，防止老化高峰导致转发抖动（Jitter）。
内存与并发：利用 原子引用计数（Refcnt） 解决逻辑删除与物理释放的冲突。利用 RSS 对称 Hash 实现无锁化处理。
异常防御：针对分片包设置 独立 Buffer Pool 和 超短老化时间，防御分片攻击。

流表的老化 (Aging)
问题：如果 500 万个终端里有 100 万个异常掉线了，没发下线包，你的内存会被撑爆。
方案：不能遍历 500 万个流（太慢）。
优化：通常使用 分级时间轮（Timing Wheel）。
把相同过期时间的流挂在同一个轮子的刻度上。
每秒钟只转动一个刻度，只处理该刻度下的流。

分协议回收：UDP 这种“无状态”的，给 30 秒老化；TCP 这种有状态的，根据 FIN/RST 报文实时回收。
LRU（最近最少使用）算法：如果 65535 个端口真满了，通过 LRU 强制踢掉那个最久没活动的流。

1.RSS（接收端缩放）与五元组 Hash
对网卡做对称哈希配置,让原始流和nat流同一个五元组的包永远都只进一个cpu,这样就不需要加锁
网卡硬件功能：网卡收到包后，会自动对五元组（源IP、目的IP、源端口、目的端口、协议）做 Hash。
对称 Hash（Symmetric Hash）：这是网关的关键。你要配置网卡，使得 A -> B 和 B -> A 的 Hash 结果指向同一个 CPU 核心。
意义：同一个 Session 的正向流和反向流都在同一个核上。这样你处理 NAT 转换时，完全不需要加锁，因为这个流表项只被这一个核管。

2. 分片重组的“陷阱”
分片包没有端口号：IP 分片的后续包只有 IP 头部，没有 UDP/TCP 端口。
问题：网卡做 Hash 时找不到端口，会导致分片包被投递到错误的核上，导致无法重组。
解决思路：
方案 A（软件重定向）：核 0 收到分片包，发现自己处理不了，通过 DPDK 的 rte_ring 转发给负责该 IP 的核。
方案 B（硬件辅助）：配置网卡只针对双元组（源/目的 IP）做 Hash（牺牲了一定的负载均衡性，但解决了分片问题）。
