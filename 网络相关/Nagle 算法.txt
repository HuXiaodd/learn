Nagle 算法是 TCP 里一个默认开启的「小包合并」机制，1984 年由 John Nagle 提出（RFC 896）。

一句话定义
在上一个数据包还没被对方确认（ACK）之前，暂缓发送下一个小包，攒到一定量再一起发。

它要解决什么问题
早期网络里有个经典毛病叫「小包风暴」：比如 telnet 远程敲字，每敲一个字母就发一个只有 1 字节有效数据、但带 40 字节 TCP/IP 头的包。如果应用傻乎乎地一个个发，网络上会充满这种「头比数据还大几十倍」的小包，带宽被头部开销浪费掉，还可能把路由器打挂。

Nagle 就是为此设计的：别急着发小包，攒一攒。

具体规则（伪代码）
plaintext

if (有未确认的数据在途) {
    if (当前待发数据 < MSS(一个包最大容量)) {
        先攒着，不发送；          // 等 ACK 回来，或攒满 MSS 再发
    } else {
        发送；
    }
} else {
    发送；                        // 没有在途数据，直接发
}
简单说就是：同一时刻最多只允许一个"小而未确认"的包在途。

为什么它反而拖慢 HTTPS
Nagle 的本意是「合并小包省带宽」，但它有个前提假设：对端会尽快 ACK。

可现实里对端（比如 nginx）为了自己也省包，常用「延迟 ACK」——收到数据后故意等最多 40ms，看看有没有数据要一起回，顺便捎带 ACK。

于是出现死等：

plaintext

客户端发 ClientKeyExchange（小包，Nagle 允许发出，因为它自己还没"未确认"的包）
   → 服务端延迟 ACK（拖 40ms）
客户端想发 CCS + Finished（小包），但上一个还没被 ACK → Nagle 不让发，卡住
   → 40ms 后 ACK 才到，客户端才发下一段
Nagle 的「攒包省带宽」和延迟 ACK 的「攒 ACK 省包」撞在一起，每段硬生生多等 ~40ms。对 HTTPS 握手、HTTP 请求这种「短、小、交互式」场景，这是纯亏。

结论
Nagle 的价值：大块流式传输、或小包高并发会打爆网络的老式场景，省带宽、护路由。
Nagle 的代价：交互式/请求-响应式场景，牺牲延迟换带宽。
TCP_NODELAY 就是把这个默认算法关掉，让应用「想发就发」——这正是我们优化①做的事。
一句话总结：Nagle = 用延迟换带宽的攒包开关；关掉它（TCP_NODELAY）就是拿带宽换回低延迟
************************************
RTT = Round-Trip Time（往返时延）​，指一个数据包从发出、到收到对方回应，这一来一回所花的时间。

通俗理解
就像打电话："你说一句话 → 等对方回答" 这一个来回的耗时，就是 1 个 RTT

工作的网络优化中包含的知识:
优化了Nagle算法对于https请求的耗时
### 优化① TCP_NODELAY —— 收益最大

TLS 1.2 握手第 3 步，客户端要连续发出三个小段：`ClientKeyExchange`（约 150 字节）、`ChangeCipherSpec`（1 字节）、`Finished`（约 40 字节）。

Nagle 开启时，**后面的小段必须等前一个小段被 ACK 才允许发出**；nginx 默认延迟 ACK 40ms。于是链路被无谓拉长：

```
客户端发 ClientKeyExchange
   → 服务端延迟 ACK（拖 40ms）
客户端才能发 CCS + Finished
   → 服务端要收齐 Finished 才能回自己的 Finished（再拖 40ms）
```

`TCP_NODELAY` 关掉 Nagle 后，小段立即发出、不再互相等待，这几处 40ms 停顿直接消失。第 ④ 步发请求同理（请求行 + 多个头都是小段）。

### 优化② 合并写 —— 减少小段数量

把"请求行 + 5 个头 + 空行"约 10 多次 `mbedtls_ssl_write` 合并成 1 次。效果：
- 段数从 10+ 降到约 2（头 1 段 + body 1 段）；
- 每个 TLS record 都有 5 字节头 + GCM tag + 填充开销，段少即省；
- 与优化① 叠加后，请求头几乎"一条 record 直接发完"。

### 优化③ 会话复用 —— 只对"第二次及以后"生效

完整握手（2 RTT）要做 RSA 验签 + ECDHE 等最贵的非对称运算。握手成功后缓存 session ticket，第二次连同一域名时带上 ticket，服务端直接认出：
- 跳过证书 + 密钥交换；
- 复用主密钥；
- 握手 2 RTT → 1 RTT，且双方不再做 RSA/ECDHE。
