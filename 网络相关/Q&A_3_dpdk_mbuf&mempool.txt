2.numa和cpu的关联到底是什么,为什么说这里保存了numa_id就确
保了内存亲和性呢?
答：
socket_id其实是cpu-内存的一条会话通路,有几个cpu就有几个numa节点即为socket。
关联性：在一个多路服务器中，CPU 核心是被物理划分在不同的插槽（Socket）上的。每个 Socket 都有自己直连的内存条，这被称为 NUMA 节点。
为何确保亲和性：socket_id 记录了该内存池物理内存所属的节点 。
如果 CPU 核心访问本 Socket 直连的内存（通过 socket_id 匹配），延迟最低。
如果 CPU 访问跨 Socket 的内存，必须经过总线（如 Intel 的 UPI/QPI），延迟会大幅增加，在高并发下会成为瓶颈。
结论：保存 socket_id 是为了让分配器尽量从靠近 CPU 的地方取“子弹”，避免跨 Socket 访问产生的性能损耗 。

关于mempool的get过程
当你调用该函数时，系统内部会经历以下三个逻辑阶段：

阶段 A：检查本地缓存 (Local Cache) 
获取缓存：函数首先通过当前核心的 lcore_id 找到对应的 struct rte_mempool_cache 。
快速出队：如果本地缓存中有闲置的指针（cache->len > 0），它会直接从 cache->objs 数组的末尾弹出一个指针返回给用户 。
性能优势：这一步完全在 CPU 私有缓存中完成，无锁、无跨核通信，耗时极短。

阶段 B：后端“进货” (Backend Dequeue) 
触发条件：如果本地缓存为空，或者根本没有配置缓存。
调用 Ops：通过 ops_index 找到对应的出队函数（例如 common_ring_sc_dequeue）。
批量获取：为了平摊由于竞争全局资源（如 Ring 的原子操作）带来的性能开销，它通常不会只取 1 个，而是尝试一次性取出一整块（通常是 cache->size 个）对象填充到本地缓存中 。

阶段 C：返回结果
如果最终成功获取到对象，返回 0；如果后端仓库也空了，则返回错误代码（如 -ENOENT）。

关于mempool_get中的
第一阶段：Local Cache 的“栈”式操作（LIFO）
在源码中，local_cache 实际上被当作一个后进先出（LIFO）的栈来使用：
逻辑：它从 cache->objs 数组的末尾（Top）取值 。
深度原因：这样做是为了热缓存命中（Cache Warmth）。最近刚刚放回（Put）内存池的 mbuf，其结构体内容很可能还在 CPU 的 L1/L2 缓存里。立即把它再取出来（Get）给下一个报文用，能实现极高的执行效率。
第二阶段：后端环形队列的“批量补给”
当本地缓存空了（cache->len == 0），它会触发 ops->dequeue ：
这一步好理解,后进先出,最后入的数据一定是最"新"的数据,按照cpu的cache命中原则去看只要大小符合一个cache line,越新的数据越容易命中.

批量（Bulk）行为：它不会只去 Ring 里取 1 个，而是根据配置（通常是 cache->size）尝试取出一整批（比如 32 个） 。
原子竞争：这一步会涉及到 rte_ring 的原子操作（如 CAS）。由于是批量取，多个核心竞争同一个环形队列的频率被降低了 cache->size 倍。
第三阶段：无缓存的回退方案
如果创建 mempool 时禁用了 local_cache（cache_size = 0） ，每次 get 都会直接去撞底层的 Ring。对于你的高性能网关，这绝对是要避免的禁忌
这一步也非常好理解,取一次取一片,避免多次取触发cas去移动环指针位置.

归还流程:先看有没有cache,没有就直接还给ring,有cache就还给cache,然后看是不是超过阈值了,如果超过阈值了,就把顶端元素还给ring.

static __rte_always_inline void
rte_mempool_do_generic_put(struct rte_mempool *mp, void * const *obj_table,
			   unsigned int n, struct rte_mempool_cache *cache)
{
	/* 第一步：如果没有缓存，直接放回后端“仓库”（Ring） */
	if (unlikely(cache == NULL)) {
		rte_mempool_ops_enqueue_bulk(mp, obj_table, n);
		return;
	}

	/* 第二步：将对象放入本地“口袋” (LIFO 栈) */
	void **cache_objs = &cache->objs[cache->len];
	for (unsigned int index = 0; index < n; index++)
		cache_objs[index] = obj_table[index];
	cache->len += n;

	/* 第三步：关键点！检查“口袋”是否太满 (Flush Threshold) */
	if (cache->len >= cache->flushthresh) {
		/* 如果超过阈值，将多出的部分倒回后端“仓库” */
		rte_mempool_ops_enqueue_bulk(mp, &cache->objs[cache->size],
					     cache->len - cache->size);
		cache->len = cache->size;
	}
}

对于使用完mbuf并还给cache时为什么不会内存溢出:
标准收发包：通常是 32 或 64。
cache_size：通常是512,cache的阈值是1.5倍size.
框架上限：很少有应用会尝试在一个函数调用里同时 free 超过 256 个 mbuf
所以这个cache的大小被设置在512*2是合理的----单批次不会超过256个
